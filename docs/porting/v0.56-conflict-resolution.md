# v0.56 移植冲突处理报告

本报告只聚焦**移植过程中产生冲突、需要人工合并**的代码。逐个说明:
冲突位置、双方(upstream v0.56 vs yanhuang v0.51)各自的功能、
以及最终如何合并。

移植方式:以 `vector/v0.56` 为基底,应用 yanhuang 自定义 diff
(`git apply --3way`)。多数文件自动干净应用,以下是需要人工介入的部分。

## 冲突一:`lib/file-source/src/file_watcher/mod.rs`

这是唯一涉及**逻辑合并**的冲突,因为双方都在改 `FileWatcher` 读取 EOF
时的行为。共 3 处。

### 双方功能说明

| 方 | 功能 | 引入的字段/方法 |
|----|------|----------------|
| **upstream v0.56** | **EOF 指数退避**:读到 EOF 后,按 1ms→250ms 指数递增重试间隔,避免对空闲文件空轮询、降低 CPU | `read_retry_delay: Duration` 字段;`track_read_eof()` 方法(设置退避 + `reached_eof=true`);`should_read()` 中据此判断是否跳过本次读取 |
| **yanhuang v0.51** | **EOF linger line**:文件最后一行没有换行符时,等待一段时间后仍把这半行数据吐出来(否则会永远卡住不输出) | `read_eof_linger_line: bool`、`data_ready_time: Instant` 等字段;EOF 分支里读取残余 buffer |

### 冲突 1a — 结构体字段(约 line 64)

```
<<<<<<< ours (v0.56)
    read_retry_delay: Duration,
=======
    data_ready_time: Instant,
>>>>>>> theirs (yanhuang)
```

**性质**:两个独立字段,无语义冲突,只是 diff 落在相邻行。
**合并**:两个都保留。

### 冲突 1b — 结构体初始化(约 line 190)

```
<<<<<<< ours
    read_retry_delay: EOF_READ_BACKOFF_MIN,
=======
    data_ready_time: Instant::now(),
>>>>>>> theirs
```

**合并**:同上,两个初始值都保留。

### 冲突 1c — EOF 读取分支(核心,需要真正动脑)

三方对比(diff3):

**base (v0.51 原始)** —— 读到 EOF 只是标记,不吐数据:
```rust
self.reached_eof = true;
Ok(RawLineResult { raw_line: None, discarded_for_size_and_truncated })
```

**ours (v0.56)** —— 用 `track_read_eof()` 替代裸赋值,加入退避:
```rust
self.track_read_eof();   // 内部会 set reached_eof=true 并更新 read_retry_delay
Ok(RawLineResult { raw_line: None, discarded_for_size_and_truncated })
```

**theirs (yanhuang)** —— 保留裸赋值,但加了 linger line 分支:
```rust
self.reached_eof = true;
if self.read_eof_linger_line && !self.buf.is_empty() {
    // 吐出没有换行符的残余行
    Ok(RawLineResult { raw_line: Some(RawLine { offset: initial_position,
        bytes: self.buf.split().freeze() }), discarded_for_size_and_truncated })
} else {
    Ok(RawLineResult { raw_line: None, discarded_for_size_and_truncated })
}
```

**合并策略**:两个功能语义正交 —— 退避只影响**下次读取的调度节奏**,
linger 只影响**本次是否吐残余行**。因此:
1. 采用 v0.56 的 `track_read_eof()`(获得退避能力);
2. **删掉** yanhuang 手写的 `self.reached_eof = true`,因为
   `track_read_eof()` 内部已经设置了它,避免重复;
3. 保留 yanhuang 的 linger line 分支。

最终结果:
```rust
self.track_read_eof();
if self.read_eof_linger_line && !self.buf.is_empty() {
    // eof linger line read flag is set, get the linger line.
    Ok(RawLineResult { raw_line: Some(RawLine { offset: initial_position,
        bytes: self.buf.split().freeze() }), discarded_for_size_and_truncated })
} else {
    Ok(RawLineResult { raw_line: None, discarded_for_size_and_truncated })
}
```

**行为影响**:linger line 的**内容**不变,但被吐出的**时机**现在受
v0.56 退避影响(最长可能延迟 250ms)。需回归"写入无换行行后等待
linger 输出"的场景。

## 冲突二:`src/internal_events/exec.rs`

### 双方功能说明

| 方 | 改动 |
|----|------|
| **upstream v0.56** | 给所有内部事件统一加 `#[derive(NamedInternalEvent)]`;`counter!` 宏第一个参数从字符串字面量改为 `CounterName` 枚举 |
| **yanhuang v0.51** | 在 `ExecFailedError` 前插入了自研的 `CronJobError` 事件(cron 表达式解析失败时上报) |

### 冲突 — derive 属性(约 line 43)

```
<<<<<<< ours (v0.56)
#[derive(Debug, NamedInternalEvent)]
=======
#[derive(Debug)]                    // yanhuang 给 CronJobError 用的旧 derive
pub struct CronJobError<'a> { ... }  // 一整块自研代码
impl InternalEvent for CronJobError<'_> { ... }
#[derive(Debug)]                    // 这是 ExecFailedError 的 derive
>>>>>>> theirs (yanhuang)
pub struct ExecFailedError<'a> {
```

**合并**:
1. 保留 yanhuang 的整块 `CronJobError`;
2. 给 `CronJobError` 也套上 v0.56 的 `#[derive(Debug, NamedInternalEvent)]`;
3. `ExecFailedError` 恢复 v0.56 的 `#[derive(Debug, NamedInternalEvent)]`。

### 连带编译修复 — `counter!` API(合并后 `cargo check` 报 E0308)

`CronJobError` 里仍是旧写法 `counter!("component_errors_total", ...)`,
v0.56 要求 `CounterName` 枚举,报 `expected CounterName, found &str`。
因 `CounterName::ComponentErrorsTotal` 恰好映射为字符串
`"component_errors_total"`(见 `metric_name.rs:270`),**语义完全等价**,
故改为:
```rust
counter!(
    CounterName::ComponentErrorsTotal,   // 原:"component_errors_total"
    "schedule" => self.schedule.to_owned(),
    "error_type" => error_type::CONFIGURATION_FAILED,
    "stage" => error_stage::RECEIVING,
).increment(1);
```
**行为影响**:指标名不变,下游 dashboard/告警无需改动。

## 冲突三:`website/assets/js/search.tsx`(以及连带的 package.json / data.html)

### 判定:yanhuang 端是损坏的合并残留,不是真实功能

排查发现 yanhuang 分支里这几个 website 文件本身就是坏的:
- `search.tsx`:重复的 `import`(第 1-2 行与 3-4 行完全一样)、
  重复的 `const Result` 声明 —— 根本无法编译;
- `package.json`:**重复的 `"crypto"` key**(破坏 JSON 合法性),
  `typesense-sync` 插在破坏字母序的位置;
- `data.html`:仅仅删掉了文件末尾换行符,无意义。

三者是同一次历史 botched merge(`#21216 [WEB-5244] Updates website
search logic`)的产物。而 Typesense 搜索功能本身在 upstream v0.51/v0.56
里**早已存在且正常**。

### 合并策略

**不移植这段损坏 diff,直接采用 v0.56 干净版本**
(`git checkout vector/v0.56 -- <file>`)。没有功能损失。
